# Design Decisions

Quick reference for non-obvious choices. Each entry answers "why did we do it this way?"

---

| Decision | What we chose | Why |
|---|---|---|
| **LLM provider** | OpenAI gpt-5-nano | Gemini 2.5 Flash free tier has a 20 req/day hard limit. This limit was exhausted in the first test run (~10 articles). Paid OpenAI at nano pricing runs 864 articles for ~$0.13–0.15 total. |
| **Structured output** | Pydantic + `with_structured_output()` | Early versions asked the LLM to "return valid JSON." Models returned malformed JSON (markdown fences, trailing commas, explanatory text). Required 30+ lines of fragile repair logic. Pydantic schema enforced at API level eliminates all of that. |
| **Pipeline built once** | Before the item loop, not inside it | `llm.with_structured_output()` construction is not free. Building it inside a loop of 864 items added measurable overhead. Built once and reused across all items. |
| **Fuzzy match threshold = 82** | High threshold | At threshold 70: "IndiGo" matched "Indo-National" (NIPPOBATRY.NS), "SpiceJet" matched "Spacenet Enterprises" (SPCENET.NS). Threshold 82 eliminates these while true matches (Sun Pharma → SUNPHARMA.NS, L&T → LT.NS) still resolve correctly. The alias dictionary handles short names that genuinely score below 82. |
| **Null ticker preserved** | Signal kept with `ticker = null` | Unresolved tickers still carry valid LLM signals (event type, sentiment, key claim). Discarding them wastes the LLM call. Null-ticker signals are preserved for potential name-based lookup in Phase C or D. |
| **Max candidates = 25** | Top 25 by \|score\| | 104 tickers passed the minimum score threshold. 15 was too narrow — missed tickers ranked 16–25 that had strong signals. 25 is reasonable Phase C coverage without the deep-dive becoming too slow. |
| **Sort by \|score\| not score** | Absolute value | A score of −60 (ACC with earnings miss signals) is as actionable as +75 (BHEL with earnings beat). Sorting by absolute value ensures both strong buy and strong avoid candidates surface in the top 25. |
| **Content filter: 40-char body minimum** | Additional to 80-char total | 27 RSS articles from Investing.com and Yahoo Finance passed the 80-char total filter but had empty or near-empty summary fields ("Click to read more", null). These reached the LLM with no content and produced either empty signals (wasted call) or hallucinated signals (noise). The 40-char body filter blocks them. |
| **Sector bonus applied in Phase C** | After market_data.py fetch | yfinance sector labels are fetched in Phase C. Running a separate batch yfinance call during B3 just for sectors would duplicate Phase C's work and add time to Phase B. The compromise: B3 scores on signal strength only; Phase C applies sector alignment after fetching market data. |
| **Output in dated folders** | `output/{YYYY-MM-DD}/` | Each daily run produces a self-contained snapshot. Dated folders mean yesterday's data is never overwritten, runs are easy to compare, and partial re-runs (e.g. re-running Phase B with `--skip-signals`) read and write to the same day's folder. |
| **LLM logs in `phaseB/signal_logs/`** | Inside phaseB output | LLM logs (prompt + response per article) are Phase B artifacts. A top-level `logs/` folder groups them with unrelated system logs. Placing them in `phaseB/signal_logs/` makes the provenance clear and keeps all Phase B outputs together. |
| **ticker_extractor in `utils/`** | `context_ext_layer/utils/` | Ticker resolution is used internally by Phase B's news_signal_extractor but is not a pipeline step. Separating it into a utilities folder distinguishes support code from pipeline modules and makes it importable by future phases (C, D) without importing from phaseB_CS. |
| **RSS title-only articles filtered** | Require body ≥ 40 chars | RSS feeds are "thin" sources — titles + summaries only, no full article body. Sending a title-only item to the LLM wastes a call. Phase B uses RSS for signals where the summary is substantive enough (≥40 chars) to contain an actual claim. For deeper content on RSS articles, `generic.py` can fetch the full page by URL. |
| **screener.in scrape (no API)** | Web scrape via BeautifulSoup | screener.in has no public API. The web scrape is the only way to get the 10-year financial tables. The `--skip-screener` flag exists because it is the slowest Phase C step (~10–15 sec/ticker) and can be skipped when only market and signals data is needed. |
| **Entity-centric signal schema** | `entity_type` ∈ `{listed, private, sector, macro, policy}` | Original schema assumed every extracted signal maps to an NSE ticker. But ~40% of signals from quality sources are about Zepto (unlisted), RBI rate decisions (macro), PLI schemes (policy), or "quick-commerce ecosystem" (sector theme). Discarding these loses real intelligence. The entity-centric schema preserves all signals — listed ones get ticker resolution, others flow as thematic targets into Phase D. |
| **Thematic targets → Proxy Mapper (Phase D)** | LLM maps each theme to 3–5 listed proxies | Thematic targets (private companies, sector themes, macro events) have no NSE ticker but are high-signal. Rather than discard them, Phase D asks an LLM: "which NSE-listed companies are most directly impacted by this theme?" Resolved proxy tickers are merged into the candidate list and forced into Phase C regardless of their raw signal score. This ensures macro-driven opportunities surface even when the underlying news didn't mention any listed company. |
| **Evidence card (Phase E)** | One aggregated JSON per ticker, not 8 separate files | Phase C produces 8 separate output files per ticker (market_data, screener_in, peer_comparison, etc.). The analyst LLM (Phase F) needs ONE structured input per call. Passing 8 file paths to the LLM is impractical — it can't read files. Passing 8 raw JSON dumps inflates the context with irrelevant fields. Phase E is a pure-Python aggregation step that extracts the relevant fields from all 8 files and assembles a compact, analyst-ready card per ticker. |
| **Single analyst agent for v1** | One LLM call per ticker, sees only that ticker's card | A multi-agent ensemble (regime specialist + fundamental analyst + valuation analyst + risk analyst debating each stock) would produce higher-quality recommendations but is much more complex to build and debug. For v1, a single disciplined analyst with a well-structured prompt and strict decision rules is sufficient to produce invest/watch/avoid calls with cited evidence. Multi-agent ensemble is deferred to v2 once the shape of the output is validated. |
| **CIO synthesis (Phase G1)** | Single LLM call over all analyst views | Phase F analysts each see ONE stock in isolation — they cannot know that 7 of 12 invest calls are in the same sector, or that two picks are proxies for the same theme. Phase G1 is a single LLM call that sees ALL analyst views together. Its job is not re-analysis but synthesis: pick the 3–5 worth acting on today given sector concentration, theme overlap, regime alignment, and portfolio state. This is the highest signal-to-cost LLM call in the pipeline (~3K tokens in, ~500 out). |
| **Parallel processing: threads not processes** | `ThreadPoolExecutor`, not `multiprocessing` | LLM API calls and web scraping are I/O-bound (waiting on network). Python's GIL does not block I/O. `ThreadPoolExecutor` shares memory (the pipeline object, the NSE symbol dict) and has negligible startup overhead. `multiprocessing` would require pickling the LangChain pipeline and re-importing all modules per process — significant overhead for no gain on I/O-bound work. |
| **Phase B/D/F workers=25/15/10 vs Phase C workers=3** | Different defaults per phase | LLM phases hit a single API endpoint with high RPM limits (gpt-5-nano: 5000+ RPM on paid tiers). 25 concurrent workers is safe. Phase C hits 4+ different third-party websites concurrently per ticker (yfinance, screener.in, NSE filings). screener.in in particular blocks scrapers aggressively — more than 3–4 concurrent connections risks IP ban. Per-source delays are preserved inside each ticker's worker thread. |
| **Phase D runs before Phase C** | Pipeline order: A → B → D → C | Phase D uses Phase B's thematic targets to generate proxy tickers. These proxy tickers must be in the candidate list before Phase C runs so they also get the deep-dive treatment. If Phase D ran after Phase C, proxy tickers would never get their fundamental data fetched. The unusual B → D → C ordering is intentional. |
| **`--skip-to` uses a phase index list** | `_PHASES = ["A","B","D","C","E","F","G"]` | The phase execution order is not alphabetical (D before C). Using a list with `_phase_index()` makes the skip logic correct for this non-obvious ordering. A dict or alphabetical sort would give the wrong skip behaviour for `--skip-to C` (would skip D, which should already have run). |

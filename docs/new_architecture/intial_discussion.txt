Layer 2
Layer 2 source code doesn't exist — only cached .pyc files from another branch. Here's what it was supposed to do (from reading the compiled logic):

Q: What's the significance of L2? Why not just pass raw data to L3?
Two reasons that are genuinely valuable:

Deduplication — the same article is fetched by RSS AND moneycontrol AND newsdata_io. Without dedup, L3 runs 3× the LLM calls on identical content. SHA fingerprint dedup is fast and worth keeping.
Quality filtering — articles with <100 chars or no date are noise. Filtering before LLM calls saves cost.
Q: How does dedup work — keyword or hash?
SHA-256 of clean text (not keywords). Smart — language-agnostic and cheap to compute.

Q: What's quarantine.json?
Records that fail quality checks — too short, no publication date, unparseable encoding. Three fields: record_id, reason (too_short / no_date / decode_error), source_module. Do you need it? Only for debugging. Can be removed from production.

Q: 540 → 530, where did 10 go?
10 records were quarantined or detected as near-duplicates (SHA fingerprint match). That's the dedup working correctly.

Q: layer2_manifest vs quality_report — should they merge?
Yes. The manifest tracks output file paths; the quality report tracks record counts. They should be one run_summary.json.

Layer 3
Q: Why 830 entities from 540 docs?
One document can mention multiple companies. A single Moneycontrol article about "TCS and Infosys both beat estimates" yields 2 entities. At an average of ~1.5 entities per doc, 540 × 1.5 = 810, close to 830. Not chunks — just multiple entities per document.

Q: How are chunks made?
Hardcoded max 3,500 characters, split at sentence boundaries. A 10,000-char article → 3 chunks → 3 LLM calls. Short articles (< 3,500 chars) → 1 chunk → 1 LLM call. Headlines (<200 chars) get batched 8 at a time into 1 call.

Q: Why 509 processed, 507 LLM, 4 rule-based?

540 input records
21 skipped as duplicates (SHA dedup from L2)
509 remain for processing
4 are structured records (FII/DII numbers, bulk deals) → rule-based extractor, no LLM
505 text documents → routed to LLM, 507 because some structured records also run a light LLM pass
The 2 gap is rounding in the counter.
Q: Do LLM logs have full prompt + response?
No — only summary stats (doc_id, chunk_id, counts of extracted objects, errors). This is a gap. If you want to debug hallucinations you need the actual prompts logged.

Q: Are all 5 object types extracted by one LLM call?
Yes — one prompt per chunk extracts entities + facts + claims + events + themes simultaneously. This is efficient (1 call not 5) but means the prompt is complex.

Q: What's contradiction_hints.json?
100% rule-based. If fact_card says "Infosys revenue grew 15%" and another fact_card says "Infosys revenue fell 3%", the contradiction detector flags it by entity name + metric. No LLM involved.

Q: Are there unnecessary IDs?
Chunk IDs are unnecessary — they're created during extraction and no downstream layer ever uses them. After L3, only document_id and object_id (entity_id, fact_id, etc.) matter. Chunk IDs add complexity with zero downstream value.

Layer 4
Q: Why so many output files?
9 files when 1 would do. The only file anyone downstream reads is memory_context_packet.json. Everything else (memory_candidates.json, memory_decisions.json, new_memory_records.json, etc.) is audit logging written for debugging. All can be collapsed into a single layer4_summary.json.

Q: How does memory recall work?
Entity name lookup in entity_memory_index.json (a dict: {"infosys": ["MEM_001", "MEM_045"]}) → fetches those memory records. Not semantic search, not vector similarity — just string matching on entity name. Simple and works for now but will break if entity names vary ("Infosys" vs "Infosys Ltd").

Q: How many LLM calls?
Zero. Entirely rule-based. Scoring is a formula, recall is index lookup.

Q: Is the memory context packet enough context for L5?
Partially. It returns past memory objects but strips the original supporting text. So L5 knows "Infosys was watchlisted 2 weeks ago" but not "because revenue guidance was cut by 5%". The original context is lost in the compression. This is a real gap.

Layer 5
Q: What is L5 doing exactly?

Groups related signals together — e.g., all mentions of "US tariffs on software" → one signal group
LLM call per group: "Given these grouped signals, what's the investment hypothesis?" → returns structured hypothesis with beneficiaries, time horizon, deep-dive questions
Separately: rule-based market regime assessment (is market bullish/bearish/neutral based on FII flows, volatility, breadth)
Q: Is there hardcoding?
Yes — meaningful hardcoding:

Priority scoring weights (investment_relevance: high=30, medium=15, low=0)
Max 50 LLM calls per run (cap to control cost)
Signal grouping thresholds
These are all tunable but need manual changes to the source code. Not great long-term.

Layer 6
Q: Is ranking hardcoded?

Score ≥80 → deep dive, <35 → reject
These numbers were chosen by judgment, not learned from data. They work but are brittle — if you want to prioritize long-term plays the whole scoring table needs to change.

Q: How are watch/reject/deep_dive decisions made?
Pure rule: priority_label from scoring → mapped to action. No LLM, no learning.

Layer 8
Q: Is evidence building LLM or rule-based?
Entirely rule-based. It joins L3 intelligence (what was said about this company) + L7 data (actual numbers) + L5 hypotheses (what we expected to find) → produces structured evidence cards. No LLM calls. Pure Python logic.

Q: Is data duplicated in agent_context_packets?
Yes, intentionally — each packet is a self-contained brief for one agent so the agent doesn't need to fetch from other files. The duplication is acceptable for LLM consumption but the packets contain a subset, not the full dump.

Layer 9
Q: What do the 4 agents actually do?

Agent	Question it answers	LLM schema
fundamental_agent	Is this a quality business? Revenue quality, margins, moat, mgmt	FundamentalAssessment: score 0-100 per dimension, key findings, risks
valuation_agent	Is it cheap or expensive vs peers/history?	ValuationAssessment: P/E vs sector, upside to target, value label
risk_agent	What are the real risks? Data gaps? Red flags?	RiskAssessment: risk severity per category, critical_data_gaps
thesis_validation_agent	Given the above 3, does the original hypothesis hold?	ThesisValidation: supports/neutral/contradicts, updated confidence
Thesis agent runs LAST and receives the previous 3 assessments as context — so it integrates them. That's the right design.

Q: How many LLM calls?
4 agents × 7 targets = 28 calls. All parallel-capable but currently run sequentially per agent type.

Layer 10
Q: What are the 14 LLM calls?

7 × target synthesis (one per target: "given everything, what's the final view?")
7 × scenario building (one per target: "what's the bull/base/bear case?")
Everything else (scoring formula, recommendation policy, confidence calibration, memory instructions, report writing) is rule-based.

Q: How does the scoring formula work?


score = 0.25×fundamental + 0.20×valuation + 0.20×thesis + 0.20×(100-risk) + 0.15×market_alignment
      − penalties (for each: data_gap>3 → -5, high_risk_flag → -8, agent_disagreement → -4)
All hardcoded weights. The final label (research_candidate / watchlist / avoid / too_speculative) is then applied by a rule-based policy engine.
